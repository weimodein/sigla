1.4. Scope and Delimitation

The proponents developed SigLa: A Mobile Sign Language Translator Application for Persons with Speech and/or Hearing Disabilities. SigLa supports one-way communication by translating supported Filipino Sign Language (FSL) gestures into text and voice. The application aims to help users communicate their basic needs and participate in everyday interactions. Gesture recognition runs on the device after the recognition model and its label map have been downloaded. The label map connects model outputs to words. Internet access is required to update models, synchronize words and categories, and stream or download demonstration videos. Offline voice output requires a suitable English text-to-speech voice on the device. The web-based administrator platform connects to the backend services through the internet. PostgreSQL stores word details, gesture data, administrator accounts, model information, and activity records, while model and media files are kept in separate file storage.

The system has three (3) types of users: the Super Administrator, the Administrator, and the Mobile User. The super administrator manages administrator accounts and has access to the dashboard, categories, words, recognition models, activity logs, reports and analytics, and account settings. The administrator has access to the same modules, with administrator account management reserved for the super administrator. Users with either administrator account type can update their own username, email address, and password. Mobile users access the Android application for sign-to-text and text-to-speech translation. The mobile application allows guest access upon opening.

The SigLa mobile application has four (4) main modules: Main Interface, Word Bank, Translation History, and Settings. It recognizes supported gestures from a sequence of movements and produces individual vocabulary labels. The initial model download requires an internet connection. Subsequent gesture recognition can use the saved model offline. When the recognition service starts, the application checks the deployed model and downloads the required files when an update is available. This process also applies when an administrator restores an earlier model version. The application uses a checksum, when supplied by the server, to check the downloaded model before installation. The application prepares the model and label files together before replacing the saved files. If an update is interrupted, the previous files may remain available, while the word bank may need to be synchronized again to match the installed model. The word bank usually follows the deployed model's recorded vocabulary, with an alternative selection method for older model records. The main interface displays messages during model checking, downloading, and loading. Demonstration videos can be downloaded individually or as a group for offline viewing.

When launched for the first time, the mobile application displays a short onboarding tutorial covering the main interface, gesture detection, word bank, and navigation. Users can skip the tutorial or replay it through Settings. The application saves the tutorial's completion status on the device and uses this status during later launches. Clearing the application data resets this status and allows the tutorial to appear again. After reinstallation, the tutorial's appearance depends on whether Android restores the saved application data.

The Main Interface module uses the device camera to capture gestures. Once the model is ready, the application analyzes gestures automatically and displays an accepted result in English, with its Filipino translation when available and enabled. The device's text-to-speech engine provides voice output. Users can show or hide the Filipino translation and switch between available front and rear cameras. After each accepted result, the application applies a two-second pause before accepting the next gesture. Recognition time varies with the available landmark data, gesture movement, confidence level, and consistency of predictions. Holding the emergency button for two seconds requests the spoken phrase "Help me" and displays an "Emergency alert played" message. The alert uses the saved application volume and follows the device's audio and text-to-speech settings. A retractable sidebar provides access to the other main modules.

The Word Bank module displays categories and supported words through category cards, Favorites, and All Words. Users can search for words and filter the results by category. The available words and categories depend on the server content and the deployed model. Selecting a word opens a page showing its details, available demonstration media, and a favorite button. Saved demonstration videos can be played offline, while videos accessed directly from the server require internet access. Tapping a video placeholder allows the user to save the video for offline viewing or stream it online. Selecting Download All Videos opens a confirmation dialog before the application downloads videos that still need a local copy. Users can also cancel an ongoing group download. Favorites are saved on the device, and the Favorites view displays saved selections that belong to the current word list. Saved favorite identifiers remain in local storage as the word list changes. Their availability after reinstallation or device transfer depends on the restoration of local data. A retractable sidebar provides navigation.

The Translation History module displays gestures recognized during previous sessions. Each entry shows the recognized word and its detection time. Entries are grouped by date, with the most recent entries first. The application stores up to 200 entries on the device and replaces the oldest entries as new ones are added. Users can delete individual entries by swiping or selecting the delete button. They can also clear the entire history after confirming the action. History entries remain separate from the server word bank, allowing previous records to remain when the word bank changes. Clearing application data removes the local history. History recovery after reinstallation or device transfer depends on Android backup and restoration. A retractable sidebar provides navigation.

The Settings module allows users to adjust speech volume, set a preference for a male or female voice, and switch between light and dark modes. Voice output uses the English voices available through the device's text-to-speech engine. The actual voice and its internet requirements depend on the installed engine and available voice options. Users can restore the default settings and replay the onboarding tutorial. Preferences are saved on the device and applied when changed. The application uses default values during a fresh setup and can recover saved preferences through Android backup. A retractable sidebar provides navigation.

The SigLa administrator platform provides a web-based interface for the super administrator and administrator. Users with either account type can manage categories, words, and recognition models; view the dashboard, activity logs, and reports; and update their own account details. The super administrator also manages other administrator accounts. During the initial backend setup, the system creates a super administrator account using the configured credentials or default seed values. Later startups retain the existing super administrator account. The account holder links an email address during the first-login setup. The super administrator creates other administrator accounts and provides the assigned users with their initial credentials. The setup process includes email verification through a six-digit code and credential entry before access to management modules is granted. The setup API accepts a linked email address and a password that follows the validation rules. It also accepts the existing username and the initial password when both satisfy the required checks.

The administrator platform has eight (8) modules for the super administrator: Dashboard, Manage Categories, Manage Words, Manage Model, Manage Administrators, Activity Logs, Reports and Analytics, and Account Settings. The administrator has access to seven (7) modules, with Manage Administrators reserved for the super administrator.

The login page allows users with either administrator account type to sign in using a username or email address together with a password. Selecting Forgot Password opens a password recovery page. The user enters the linked email address, verifies a six-digit code, and creates and confirms a new password. After a successful reset, the user returns to the login page. This process requires access to the linked email account. The super administrator can also set a temporary password for another administrator through Manage Administrators.

Passwords must contain at least eight (8) characters, including at least one letter and one number. The system counts consecutive login attempts made with an incorrect password. After five (5) such attempts, the account enters a five-minute cooldown. Each additional cycle of five (5) attempts increases the cooldown by five (5) minutes. A successful login resets the attempt and cooldown counts. These rules apply to both administrator account types.

The Dashboard appears after login and completion of the required account setup. It shows the current model and summary cards for words, gesture samples, and categories. For the super administrator, an additional card shows the combined total of active and deactivated administrator accounts. For the administrator, this card shows the account creation date. Summary cards with navigation actions open their related pages, while the account creation card serves as a reference. Horizontal bars display recorded accuracy for up to eight recent model versions with available results. A recent activity section shows the signed-in account's actions, descriptions, and dates. A retractable sidebar provides access to the modules available to the account.

The Manage Administrators module is available to the super administrator. It displays four summary counts: the combined total of active and deactivated accounts, active accounts, deactivated accounts, and deleted accounts. A searchable and filterable table shows account IDs, usernames, masked email addresses, statuses, registration dates, and action buttons. The super administrator can create accounts, edit usernames and email addresses, deactivate or reactivate accounts, and delete accounts. Account deletion changes the database status to deleted while retaining the account record and its activity references. A separate password reset action allows the super administrator to set a temporary password. Before returning to the management modules, the affected administrator completes the required setup, including email verification when an email address still needs to be linked. Account creation requires a username, matching password entries, and confirmation. The system records account changes and sends notification requests to linked email addresses. Delivery depends on the email service and recipient address. When an email address changes, the system can send notices to both the previous and replacement addresses. A retractable sidebar provides navigation.

The Manage Categories module is available to both administrator account types. It displays summary cards for total categories, categories assigned to words, and categories available for word assignment. Its table shows each category's name, description, word count, and edit and delete buttons. Adding or editing a category opens a form for the name and description. Before deleting a category, administrators must remove its word assignments. Administrators maintain the available category records through this module. A retractable sidebar provides navigation.

The Manage Words module allows users with either administrator account type to add, edit, and delete words, as well as manage gesture samples and demonstration videos. It displays summary cards for total words, active words, words marked ready to activate, and total gesture samples. It also includes a word table, search bar, and category filter. Word forms contain the label, Filipino translation, description, and category. Each new word starts with zero samples and awaits dataset collection and model deployment. To upload gesture clips, the administrator selects recorded videos and enters a signer ID for the person performing the gestures in that batch. Users can cancel the form before submission. Once the server accepts the upload, it processes the clips while the interface checks the progress. MediaPipe extracts hand and upper-body landmark sequences, and the system checks landmark coverage, movement, and duplicate data before storing accepted samples. Under the default ML settings, training requires at least twenty (20) unique usable clips per class, including at least four (4) identified signers with at least four (4) clips each. These settings are configurable, and the ML service checks signer coverage separately from the interface's ready-to-activate count. Model deployment updates active words based on the recorded training vocabulary. Administrators can upload a separate demonstration video and edit word details. Deleting a word removes its database entry, while related records follow the database relationships. Uploaded demonstration files remain subject to separate storage management. When edits overlap, a later successful update may replace an earlier change. A retractable sidebar provides navigation.

The Manage Model module allows users with either administrator account type to train, test, deploy, restore, and delete recognition models. It displays summary cards for total versions, deployed versions, and trained versions awaiting deployment. It also shows the currently deployed model and a table containing version details, status, accuracy, trainer, dates, and available actions. Training requires a unique version identifier containing letters, numbers, dots, dashes, or underscores. Administrators can also provide optional notes. The backend runs training as a background task while the interface checks its progress. The page keeps its Train control inactive while tracking a task, so administrators remain responsible for coordinating training requests. An interrupted training run can be recorded with a failed status and error details, which appear through the interface's status checks. The deployed model remains selected during training. Testing provides evaluation results, and the administrator decides when to deploy a model. This decision is independent of a required test step or fixed accuracy score. The training process saves results from the data split used to select the model's training duration. It then trains the deployment model using all accepted data. These results describe that evaluation setup; performance with new users and live camera input requires separate testing. Administrators can restore an inactive version while its model files remain available. Other versions can be deleted, while the deployed version is protected. Recognition model distribution begins after the first deployment. A retractable sidebar provides navigation.

The Activity Logs module gives both super administrators and administrators read-only access to recorded system actions. The table shows the administrator, action type, affected item, description, and date and time, with the newest records first. Users can filter records by action, affected item, date range, and search text. Recorded actions include account activity, category and word changes, sample operations, and model operations. The application retains logs for viewing, while record management remains at the database level. The completeness and continued availability of records depend on successful database writes, storage availability, and database maintenance. A retractable sidebar provides navigation.

The Reports and Analytics module displays summary cards for total words, gesture samples, categories, and current model accuracy. Its charts show word submissions by date, recorded accuracy by model version, and current sample totals for the ten words with the most samples. Week, month, and year controls filter the word submission trend. Sample totals represent the current data, while model metrics represent each version's recorded evaluation. The super administrator also sees additional administrator account information. The Generate Report section allows users to select word statistics, gesture sample counts, and model accuracy through checkboxes. The selected sections are exported directly as a PDF containing current totals and word or model details. The date controls apply to the word submission trend, while the exported sections use their corresponding current records. A retractable sidebar provides navigation.

The Account Settings module allows users with either administrator account type to view and update their own information. It displays the username, masked email address, account type, creation date, status, role, and account ID. The Edit Profile option allows the user to update the username and save or cancel the changes. To link or change an email address, the user enters the address and verifies a six-digit code sent to it. To change the password, the user verifies a six-digit code sent to the linked email address, then enters and confirms a new password. The password must contain at least eight (8) characters, including a letter and a number. A retractable sidebar provides navigation.

The system follows a client-server architecture composed of the SigLa mobile application, administrator platform, backend server, machine learning service, and PostgreSQL database. The mobile application requests word bank content and model updates from the backend. The backend connects the clients to the database and coordinates model training, testing, and deployment with the machine learning service. Gesture recognition runs locally on the mobile device using a downloaded TensorFlow Lite model. The backend provides a REST API for managing words, categories, models, and related updates.

The Android application uses Kotlin, while the administrator platform uses React.js. The backend uses Node.js with Express.js, and the machine learning service uses Python with FastAPI and TensorFlow. PostgreSQL stores structured records, and Supabase Storage holds model and media files. MediaPipe extracts hand and upper-body landmarks for gesture processing. The configured PostgreSQL connection determines the database host. The project uses Android Gradle, Vite, Node.js, and Python configurations to build and run its components.

Gesture recognition performance depends on the trained vocabulary, sample quality, signer diversity, device capability, camera framing, and surrounding conditions. Adequate lighting, a clean camera lens, and a clear view of the hands and upper body help the application capture useful landmarks. SigLa is intended for the FSL vocabulary represented in its dataset. It displays recognized English labels with Filipino translations when available. Its output is limited to individual vocabulary entries, including entries containing several written words. Sentence construction and continuous conversation interpretation remain outside the current scope. Gesture features are limited to hand and upper-body landmarks, with facial expressions and lip movements outside the recognition process. The application produces a result when a prediction meets its acceptance conditions and continues observing when further gesture data is needed. The accuracy of a result and the FSL validity of uploaded samples depend on dataset review and testing across users, hand structures, and signing variations.

The landmark detector processes up to two hands and supports available front and rear cameras. Gesture processing includes mirrored inputs to support variations in signing orientation. Recognition across left-handed and right-handed users depends on the trained model and evaluation data. Users should keep their hands and relevant upper body clearly visible within the camera frame. Recommending a specific camera distance requires measurements from device testing.

The Android application declares Android 7.0 (API level 24) as its minimum operating system version and requires camera hardware. Installation and performance depend on device compatibility, application libraries, available storage, and text-to-speech resources. Server-dependent features require internet access. Recommended connection speed, camera resolution, and RAM capacity should be based on device and network testing. These values remain subject to evaluation under the intended conditions of use. The current mobile implementation is developed for Android.
