3.4. Scope and Delimitation

The proponents developed SigLa: A Mobile Sign Language Translator Application that supports one-way communication from sign language users to non-sign language users. The system translates recognized sign language gestures into readable text and audible speech to assist users during daily interactions. The system stores user information, all supported word information, user-submitted words, and system analytics in a centralized database to support translation updates and system monitoring.

The system has two (2) main end-users: the mobile user and the administrator. The mobile user uses the SigLa mobile application to perform sign-to-text and text-to-speech translation, while the administrator manages the system through a web-based platform. Logging in or signing up in the mobile application is optional for general use. However, log in is required if the user intends to use the Suggest a Word feature.

Users can create an account by entering a username and email address. After submitting this information, the system sends a six-digit (6) verification code to the user's registered email address to confirm account ownership. The verification code is valid for five (5) minutes, and users are allowed a maximum of five (5) incorrect verification attempts per request. If the maximum number of attempts is exceeded, the verification session will expire, and the user must request a new verification code. If the user does not receive the code, they may request a new one by clicking the resend link. A new verification code can be sent after one (1) minute. Once the six-digit (6) verification code is entered correctly, the user can proceed to complete the registration by entering a password and confirm password, then clicking the save button to finalize the account creation. After successful registration, the system returns the user to the Sign In page, where they can log in using their registered email and password. All user information collected during registration, including the username, email address, and password, are stored securely in the system's database. Passwords are encrypted before being stored to protect user credentials. Access to user account information is restricted to authorized administrators only through the SigLa Administrator Platform.

If the user forgets their password, they can recover their account by clicking the forgot password link on the Sign In page. The user must enter their registered email address, and the system will send a six-digit (6) verification code to verify the password reset request. The same verification rules apply. The code is valid for five (5) minutes, a maximum of five (5) incorrect attempts are allowed per request, and a new code can be requested after one (1) minute if necessary. After entering the correct verification code, the user will be allowed to enter a new password and confirm password. Clicking the save button will update the password in the system, after that, the user can return to the Sign In page and log in using the updated credentials.

The SigLa Mobile Application contains several modules that support the application's functions such as Main Interface, Word Bank, Translation History, Suggest a Word, Notifications, Profile, and Settings. The SigLa Mobile Application serves as the primary interface for users. The application supports both static and motion-based gestures. The system converts recognized gestures into text and voice output, allowing the translated text to be spoken through the device's audio output to help communicate with non-sign language users. The system outputs individual words or predefined phrases and does not perform grammatical sentence construction or continuous conversational translation.

The mobile application supports Filipino Sign Language (FSL) for common daily interactions. The application can assist in daily interactions such as introducing oneself, ordering food, buying items, asking for prices, giving numbers such as age, phone numbers, or addresses, requesting assistance, asking for directions, confirming information, and communicating basic needs such as expressing hunger or thirst, indicating pain or discomfort, requesting water, food, or medicine, asking to use the restroom, and expressing feelings such as being tired, scared, unwell, and additional words. The system supports only a predefined set of words and phrases organized across defined categories and does not cover the full range of Filipino Sign Language expressions. The number of supported words is subject to change as the administrator approves new word submissions and expands the gesture recognition dataset over time.

The translation process occurs directly within the mobile application, allowing the system to function offline for gesture recognition and translation. The application requires an initial internet connection to download the base gesture recognition model. After this, gesture recognition can function offline. An internet connection is only required when the user creates an account, logs in, loads the latest notifications, suggests a new word, or synchronizes settings with the account. When the device is connected to the internet, the application automatically checks for a newer gesture recognition model in the background and downloads it only when a new version is available. The system does not provide users with manual control over model selection or rollback, as model management is handled exclusively by the administrator. Before replacing the currently active model, the system performs a model integrity verification to ensure that the downloaded model is complete and not corrupted. If the download fails or the gesture recognition model is found to be corrupted during transfer, the previously installed model remains active to ensure that gesture recognition continues to work without interruption. This ensures the system attempts to keep the model up to date.

When the user opens the SigLa Mobile Application for the first time, the system displays a brief onboarding tutorial that guides the user through the main features of the application. The tutorial introduces the Main Interface and explains how gesture detection works, how to use the Word Bank, how to submit a word through the Suggest a Word module, and how to navigate the application using the retractable sidebar. The tutorial is shown only once upon first launch and can be skipped at any time. The tutorial display state is stored locally on the device; if the application is reinstalled or the app data is cleared, the tutorial will be shown again upon the next launch. Users may also revisit the tutorial at any time through the Settings module regardless of reinstallation status.

The Main Interface serves as the primary translation screen where the user performs gesture recognition using the device camera. The interface automatically detects and translates sign language gestures as soon as the camera is active, without requiring any additional input from the user. After detecting a sign language gesture, the system displays the corresponding translated text on the screen in English along with its Filipino translation below it, and plays an audio output of the detected gesture. The user can also turn off the Filipino translation by pressing the Filipino translation button. To ensure accurate and stable detection, the system applies a two-second cooldown after each recognized gesture before accepting a new one, preventing unintended repeated detections and allowing time for the user to transition to another gesture. As a result of this cooldown, gestures typically require approximately 1 to 2 seconds to detect and translate. It includes a camera switch button that allows the user to switch between the front and rear camera for gesture detection, and an emergency button that, when pressed and held for two seconds, plays an audio alert saying "Help me" to quickly notify nearby individuals in urgent situations, preventing accidental activation while still allowing the feature to be used quickly when needed. A retractable sidebar is provided to serve as the navigation menu, allowing users to access modules such as Word Bank, Suggest a Word, Settings, Notifications, and Profile.

The Word Bank module allows users to view the list of words that can currently be translated by the application. It includes a category dropdown that allows users to filter entries based on their category, including introducing oneself, ordering food, buying items, asking for prices, giving numbers such as phone numbers, addresses or price, requesting assistance, asking for directions, confirming information, communicating basic needs, alphabets, numbers, and additional words. Selecting a sign entry plays an audio pronunciation of the corresponding word or letter. For motion gestures, it also displays a short demonstration video showing how the gesture is performed. These videos are generated from collected samples and are subject to administrator validation, but may not fully represent standardized Filipino Sign Language in all cases. The demonstration video is generated on the server from the approved gesture samples collected for that word and served to the app for playback, allowing users to visually learn how to perform each sign. For static gestures, a picture of the sign is displayed instead of a video. Users may also personalize their Word Bank experience by creating custom categories to organize their most used or favorite gestures. A create category button allows the user to add a new category with a custom name, and gesture entries can be added to these custom categories by selecting them from the existing word list. Custom categories appear alongside the default categories in the category dropdown, allowing users to quickly filter and access the gestures they use most frequently. Users may also rename or delete their custom categories at any time. Custom categories and their entries are stored locally on the device and are tied to the user account that created them. If the user logs out, the custom categories remain on the device but will only be accessible again upon logging back in with the same account. If the application is reinstalled or the user switches to a different device, custom categories will not be restored, as custom categories are stored locally and are not synchronized with the server. Application settings such as volume, voice type, text size, and display mode are synchronized with the account and will be restored upon logging in, but custom Word Bank categories are not included in this synchronization. It has a retractable sidebar and also includes a back button that allows the user to return to the main interface.

The Translation History module allows users to view a record of all gestures that have been recognized and translated by the application during previous sessions. Each entry in the translation history displays the translated word, the confidence percentage of the recognition, the gesture type indicating whether the gesture was static or motion-based, and the time the translation was detected. Entries are grouped by date, with the most recent translations appearing at the top of the list. The translation history is stored locally on the device and can hold a maximum of two hundred (200) entries. Older entries are automatically removed once the limit is reached to manage storage. Users may delete individual entries by swiping left on an entry or by tapping the delete button, and may also clear the entire translation history at once using the clear all button, which requires confirmation before the entries are permanently removed. If a word that appears in a user's translation history is subsequently deleted from the system by the administrator, the corresponding history entry is retained on the device as a local record and is not automatically removed, as translation history is stored independently of the current system word database. Translation history is stored locally on the device and will not be transferred or recovered upon reinstallation or device change. The module includes a retractable sidebar and a back button to return to the main interface.

The Suggest a Word module allows registered users to submit a new sign language gesture that is not yet included in the system. A retractable sidebar is provided, along with a back button to go back to the main interface. To submit a word, the user must enter the word and its description, specify whether the gesture requires one or both hands, and select whether the gesture is static or motion-based. Before the start collecting button becomes available, the user must check the "I have read the terms and conditions" checkbox. The terms and conditions link informs the user that their captured gesture images and the corresponding word may be displayed in the Word Bank of the mobile application if approved by the administrator, that the submitted samples may be used for training the gesture recognition model, and that submitting inappropriate or offensive content may result in account deactivation leading to permanent deletion of the user account.

Once the user checks the terms and conditions checkbox, the system normalizes the submitted word by converting it to lowercase and removing unnecessary punctuation, then checks whether the word already exists in the database. This ensures that duplicate entries caused by capitalization or punctuation differences are avoided. If the submitted word does not exist in the system, the start collecting button becomes available and the user may proceed with the gesture sample collection. Before proceeding to gesture sample collection, the user is presented with a review screen summarizing the entered word, description, number of hands, and gesture type. The user may confirm the details and proceed, or return to the form to make changes. If the submitted word already exists in the system, the application displays a prompt notifying the user that the word is already available in the database. The user may either cancel the process or continue contributing gesture samples to the existing word entry. If the user chooses to continue, the system proceeds with the data collection process and allows the user to submit gesture samples for that existing word. If the administrator locks the submission for a specific word, users will no longer be allowed to submit gesture samples for that word in the Suggest a Word module.

Once the user chooses to proceed with the collection, the system displays an instruction informing the user that gesture samples should be captured from different angles and hand positions to improve the accuracy and reliability of the gesture recognition model and that the collection process will approximately take 2 to 3 minutes. After confirming the instruction, the system begins the data collection process using the device camera. Each user is allowed to contribute a maximum of twenty-five (25) samples per word, whether the gesture is static or motion-based. Each user has a sample limit per word, and every submission adds to that total, no matter how many sessions it takes. A camera switch button allows the user to switch between the front and rear camera to provide flexibility in hand positioning and capture angle, while a cancel button allows the user to stop the collection process at any time. If the user chooses to cancel, the whole collection process will be terminated and the captured gestures will be discarded. The system performs automated validation before storing gesture samples by verifying that a detectable hand landmark structure exists and that the hand occupies a valid region of the frame. For each validated captured sample, the system performs two operations simultaneously. The image frame is saved as a photograph so that administrators can visually review and verify the submission, and at the same time the system extracts one hundred twenty-six (126) normalized hand landmark coordinates using the MediaPipe hand detection framework. These landmark coordinates represent the precise positions of the hand joints during the gesture and serve as the actual data used for training the gesture recognition model. Once all samples have been collected, the user is presented with a review screen displaying thumbnail previews of all captured samples before any data is sent to the server. For static gestures, each thumbnail shows the captured frame. For motion gestures, each thumbnail shows the middle frame of the recorded sequence, marked with a motion indicator. The user may confirm and submit all samples to the administrator for review, or choose to retake the collection, which discards all captured samples and restarts the collection process. Both the captured images and their corresponding landmark data are stored together and uploaded to the server only after the user confirms on the review screen. Before being stored, the captured gesture images are compressed to reduce their file size. This ensures that large volumes of gesture samples can be stored in the server without consuming unnecessary storage space. If no hands are detected during the collection process, the system displays a "No Hands Detected" message. All submitted gesture samples, including captured images and extracted landmark coordinates, are stored securely in the system and are accessible only to authorized administrators for the purpose of review and model training. In the event that a user account is permanently deleted from the system, the user's account information will be removed. Gesture samples that have already been reviewed and approved will be retained in the system to preserve the integrity of the gesture recognition dataset. Samples that are still pending review will be automatically rejected and removed. Samples that were previously rejected are also permanently removed upon account deletion. This applies to both new words submitted by the user and existing words to which the user contributes additional samples.

Once a user's submission for a specific word has been approved by the administrator, that user is no longer allowed to add more samples to that same word. However, if the submission is rejected, the user may submit again for the same word provided that their total contribution for that word has not yet reached the sample cap. Each user has an independent sample quota per word, meaning other users may still contribute their own samples to the same word regardless of how many samples another user has already submitted. If a user has already reached the maximum allowance for a specific word, the system will display a prompt informing the user that no further samples can be submitted for that word, although the user may still contribute gesture samples to other words that have not yet reached their required number of samples.

The Notifications module informs users about important system updates and the status of their submissions. It also delivers announcements from the administrator, including upcoming maintenance schedules, system updates, approval or denial of word submissions, warnings, and other relevant notices to keep users informed. Notifications generated by the administrator platform are stored on the server and delivered to registered users through the Notifications module of the SigLa Mobile Application. Guest users who are not logged in will not receive notifications. System announcements and submission status updates are accessible only to users with a registered account. If the user is temporarily offline, the notification will be delivered automatically once the device reconnects to the internet. An internet connection is required to load the latest notifications. The module includes a retractable sidebar to access other modules and a back button to return to the main interface.

The User Profile module allows users to manage their account information. The module provides an edit information button that allows users to update their name and username, while the registered email address remains fixed because it was verified during account registration. It also includes a change password button that allows the user to update their account password. To change the password, the user must first verify their email address by entering the correct six-digit (6) verification code sent to their registered email before inputting a new password. A save button is provided to confirm and apply any changes made to the account information. It has a logout button allowing users to securely exit. The system does not restrict simultaneous login sessions across multiple devices. However, since translation history and custom categories are stored locally, data created on one device will not be reflected on another device logged in to the same account. Application settings are an exception, as they are synchronized with the account and will be consistent across devices upon login. It also has a retractable sidebar.

The Settings module allows users to configure application preferences such as volume level, voice type, text size, and light or dark mode. The voice type setting allows users to select between a male or female voice for the text-to-speech audio output of recognized gestures. The system produces audio output in English, corresponding to the translated text displayed on the Main Interface. A reset to default button is provided to restore all settings to their original configuration. The module also includes an option to replay the onboarding tutorial for users who wish to review the application guide. For registered users who are logged in, settings are tied to the account and synchronized with the server. When a logged-in user changes any setting, the change is saved both locally on the device and to the server. When the user logs in, their saved account settings are automatically applied to the device, overwriting any local settings previously stored. This allows users to retain their preferred configuration across different devices or after reinstalling the application. Guest users who are not logged in may still configure settings, but changes are saved locally only and will not be retained across devices or reinstallations. It has a retractable sidebar, including a back button to navigate back to the main interface.

The SigLa Administrator Platform serves as the management interface of the system and requires an internet connection to access. The administrator is responsible for training, testing, and deploying the latest gesture recognition model used by the mobile application. It contains Dashboard, Manage User, Manage Word Bank, Manage Model, Reports and Analytics, and Administrator Account.

The Dashboard serves as the first page the administrator sees after logging in. It provides a quick overview of what is happening in the system. At the top, it displays a summary section showing five key pieces of information: the total number of registered users, the total number of words in the system, the number of word submissions waiting to be reviewed, the total number of gesture samples collected, and the current model version being used by the mobile application. Below the summary, a bar chart shows the number of new user registrations over time, which can be filtered by week, month, or year. Beside it, a list displays the accuracy of each trained model version, allowing the administrator to monitor whether the model performance is improving. At the bottom of the dashboard, a recent activity feed shows the latest events in the system, such as new user registrations, word submissions, approvals, and rejections. Next to it, a list of word submissions that are still waiting for review is displayed, with a review button beside each entry that allows the administrator to directly open the corresponding submission in the Manage Word Bank module. The dashboard also includes a send announcement feature that allows the administrator to create and send system announcements or notifications to all users. These announcements may include important updates, system maintenance schedules, warnings, or other relevant notices. Once sent, the announcement will be delivered to users and displayed in the Notifications module of the SigLa Mobile Application.

The Manage User module contains the list of registered users in the system. It allows the administrator to view users, add new users, update user information, deactivate accounts, or delete users when needed. The user list table includes the name, username, email address, account status, warning count, registration date and action buttons. The add user button allows the administrator to manually create a new user account by entering the user's name, username, email address, and password. Accounts created this way are not subject to email verification; however, the administrator is responsible for ensuring the accuracy of the email address entered, as it will be used for verification codes in password recovery and account-related notifications. The warn button sends a warning to users who violate the system's terms and conditions. If a user receives two warnings, the system automatically deactivates the account for thirty (30) days. The administrator may also manually deactivate an account at any time using the deactivate button, regardless of warning count. The reactivate button restores a previously deactivated account, while the edit button allows the administrator to update user information. The delete button permanently removes a user from the system. A deactivated user account will automatically be reactivated after thirty (30) days. However, if the user violates the terms and conditions again after the account is reactivated, the administrator may permanently delete the account from the system.

The Manage Word Bank module allows administrators to control and maintain all the words available in the system. Through this module, the admin can add, edit, delete, and manage gesture data for each word. When adding a new word, the admin uses the add word button and fills in the word itself, a short description, the number of hands required (one or two), the gesture type, which can be either static (a still hand position) or motion (a moving gesture), a category from the predefined list of FSL interaction categories, and an optional Filipino translation of the word. Words added manually do not have gesture samples at first, so the administrator must upload samples before the word can be activated. The administrator can also edit existing words to update their spelling, description, number of hands, gesture type, category, or Filipino translation. If a word is no longer needed, the admin can delete it, which also removes all its related gesture samples. The admin can upload gesture samples directly to any word, especially for words that were manually added. These samples are uploaded as a batch of images, and the system automatically processes each image using the MediaPipe hand detection framework to extract hand landmark coordinates, the same way it handles samples submitted by users. All samples uploaded by the admin are automatically marked as approved and counted toward the required number of samples. For a word to be activated, it must meet the minimum sample requirement: at least twenty-five (25) approved samples for static words, or at least twenty-five (25) approved sequences for motion words.

For motion gestures, the admin can generate a demonstration video using the approved samples. This video is created by the system's machine learning component and shows how the gesture is performed. The admin can generate a video at any time, even before reaching the required number of samples, to check if the gesture looks correct. Videos can be generated for a single sequence or for multiple selected sequences at once. After generating, the admin can preview the video and adjust its playback speed. Once the word has met the required number of approved samples, the admin can click set as word bank video to publish the video to the mobile app. This action activates the word, and it will appear in the mobile application after it reloads. For static gestures, no video is needed. The administrator can set a specific approved image sample as the display picture for the word by clicking the set as word bank image button in the gallery. This image will be shown to users in the Word Bank of the mobile application. Once the required number of samples is met and a display image has been set, the admin can activate the word directly using the activate button.

The module also allows the admin to review gesture samples submitted by users through the Suggest a Word feature. By opening the gallery of a word, the admin can see all submitted samples grouped by the user who submitted them, along with the status of each sample, which can be pending, approved, or rejected. When reviewing, the admin checks each sample against the following quality criteria: the hand gesture must be clearly visible, the gesture formation must be correct, the hand must be fully visible and not cut off, the camera framing must be appropriate, and the image must not contain unrelated or inappropriate content.

The admin can approve or reject samples at different levels. Individual samples can be approved or rejected one by one. All samples from a specific user can be approved or rejected at once. All pending samples for the entire word can also be approved or rejected at the same time, regardless of who submitted them. Each group of samples submitted by a user counts as one submission, and the admin can approve or reject an entire submission using the approve submission or reject submission buttons.

After a submission is reviewed, the system automatically sends a notification to the user. If only some of the samples are approved, the user is told how many were accepted and how many more they are still allowed to submit. If all samples are approved, the user is notified that their entire contribution has been accepted. If all samples are rejected, the user is advised to review the terms and conditions before submitting again. If a submission contains inappropriate or irrelevant content, the word will not be added to the system and the user will be notified.

Once enough samples have been collected and no more are needed, the admin can lock the word to stop users from submitting additional samples. Locking a word does not affect samples that are still pending review; those will continue to be processed normally. If a user has already submitted samples that are awaiting review at the time the word is locked, they will be notified of the lock status once the review is completed. Users who attempt to submit samples for a locked word will be informed by the system that submissions for that word are no longer accepted. The admin can also unlock the word later if more samples are needed.

On the user side, a user is allowed to resubmit samples for a word if their previous submission was rejected, as long as the administrator has already completed the review and the user has not yet reached their sample cap for that word. In cases where only a portion of a user's submitted samples are approved, the approved samples are immediately counted toward the user's cap, and the user may resubmit additional samples for the rejected portion, provided their total contribution has not yet reached the maximum allowed limit. Once any portion of a user's submission has been approved, only the remaining unapproved samples may be resubmitted. However, once a user's submission for a word has been fully approved, they can no longer add more samples to that same word. If the word is locked or the user has already reached their allowed number of samples, the system will show a message that no more submissions can be made for that word.

To keep the system appropriate and safe, the admin can issue a warning to a user who submits inappropriate or offensive words, uploads gesture images with inappropriate or irrelevant content, or violates the system's terms and conditions. Warnings can be issued directly during sample review in the gallery or through the manage users module. If a user receives two warnings, their account is automatically suspended for 30 days. After 30 days, the account is automatically reactivated. If the user violates the rules again after reactivation, the admin may permanently delete the account from the system.

The Manage Model module contains the list of model versions used for gesture recognition. It allows the administrator to manage the machine learning models in the system. The model list table shows the model version, accuracy, date created, and action. To train a new model, the administrator can click the train button, which starts the training process using the approved gesture datasets. After training, the administrator can click the test button to check the accuracy of the model before deploying it in the application. The administrator can activate a model by clicking the deploy button so it can be used in the mobile application. If the current model causes errors or has lower accuracy, the administrator can click the revert button to return to a previous stable model version. The system retains all previously trained model versions in the database, allowing the administrator to revert to any prior version. Model versions can only be deleted manually by the administrator using the delete button, and at least one deployed model version must remain active in the system at all times.

The Reports and Analytics module provides administrators with an overview of system activity. It displays the total number of registered users, the total number of words in the system, the number of pending word submissions, the number of gesture samples per word, user registration trends over time, and the accuracy of each trained model version. It also shows the total number of users who received warnings, the number of users with deactivated accounts, and the number of users whose accounts were permanently deleted, along with their lists. It includes filter buttons for week, month, and year that allow administrators to adjust the displayed data range to monitor system growth and user engagement over time. A generate report button is also available, allowing administrators to export a summary report of the system activity in PDF format. Before generating, the administrator can select which specific overview to include in the report, such as user statistics, word submissions, gesture sample counts, registration trends, model accuracy, warned users, deactivated users, or deleted users, and apply the week, month, or year filter to define the data range covered by the report. This allows administrators to produce focused and relevant reports for record-keeping, performance evaluation, and system monitoring purposes.

The Administrator Account module contains the administrator's account information such as username and email address. The administrator can update these details by clicking the edit profile button. After editing the information, the administrator can click the save button to apply the changes. It also has a change password button that allows the administrator to update the account password. To change the password, the administrator must first verify their email address by entering the correct six-digit (6) verification code before inputting a new password. A save button is provided to confirm and apply the new password.

The system architecture consists of the SigLa Mobile Application, SigLa Administrator Platform, SigLa Backend Server, SigLa Machine Learning Component, and PostgreSQL Database. The mobile application communicates with the backend server for account services, word submissions, and model updates. The backend server acts as the bridge between the mobile application, the administrator platform, the machine learning module, and the database. The machine learning module handles gesture recognition model training, testing, deployment, and demonstration video generation, while the database stores system data such as users, words, suggested submissions, reports, and model information. The system follows a client-server architecture where the mobile application handles gesture recognition locally using a downloaded TFLite model, while the backend server manages user data, word submissions, and model updates through a REST API.

The system is developed using Kotlin for the Android mobile application, React.js for the web-based administrator platform, Node.js with Express.js for the backend server, Python for the machine learning component, and PostgreSQL as the database management system. The system also uses Supabase as the cloud platform for database hosting and storage. Development tools used include Android Studio, Visual Studio Code, Postman, and GitHub.

The proponents recognize that gesture recognition performance can be influenced by device specifications and environmental conditions, and the system is designed to adapt and perform effectively within these factors. Devices with higher hardware capabilities may enhance performance. The system aims to provide accurate translations, but occasional inaccurate translations may occur. Recognition results may also be influenced by environmental factors such as insufficient lighting, a dirty or damaged camera lens, camera obstruction, or excessive distance between the camera and the hand gesture. The system exclusively supports Filipino Sign Language (FSL) gestures. While the Main Interface displays the translated text in both English and Filipino, this does not indicate support for any other sign language. The English translation is provided solely to make the recognized gesture more broadly understandable to a wider audience, as many FSL gestures correspond to concepts that are more commonly expressed in English. The underlying gesture recognition, the gesture dataset, and the entire translation process are based entirely on FSL. The system recognizes only sign gestures, with each recognized gesture mapped to a predefined word or phrase based on the trained dataset. Variations in hand structure, such as incomplete or irregular fingers, may affect the system's recognition accuracy. The system is designed to improve gesture recognition within its capabilities and to continuously support clear and effective gesture-based communication.

For optimal recognition, the recommended distance between the camera and the hand gesture should not exceed 0.5 meters to ensure reliable gesture recognition. The system supports left-handed and right-handed users, as well as gestures that require one or both hands. The system supports gesture recognition for up to two hands simultaneously, accommodating both one-handed and two-handed gestures.

The system requires a stable internet connection with a minimum speed of 10 Mbps for features that require server communication, such as account authentication, word submission, and model updates. The mobile application recommended minimum specifications include a 13-megapixel camera, a minimum of 6GB of RAM to ensure stable simultaneous operation of the camera, hand detection framework, and gesture recognition models, and must run on Android version 7.0 (Nougat) or higher to ensure compatibility and proper performance. The SigLa Mobile Application is developed exclusively for the Android platform and does not support iOS or any other mobile operating system.
