3.4 Scope and Delimitation

The proponents developed SigLa: A Mobile Sign Language Translator Application for Persons with Speech and/or Hearing Disability. SigLa supports one-way communication, translating Filipino Sign Language (FSL) gestures captured through a device camera into on-screen text and spoken audio so that sign language users can be understood by non-signers. It is intended as an accessible tool for everyday interactions that reduces heavy reliance on human interpreters. The system operates both online and offline, and it keeps all supported words, gesture sample data, administrator accounts, trained models, and activity records in a centralized PostgreSQL database that supports translation updates and system monitoring.

The system recognizes three (3) types of users: the Super Administrator, the Administrator, and the Mobile User. The super administrator has full access to the administrator platform, including managing all administrator accounts, viewing the dashboard, managing categories, managing words in the word bank, managing the gesture recognition model, viewing the activity logs, viewing reports and analytics, and managing its own account credentials. The administrator has the same access except for managing other administrator accounts, which is reserved for the super administrator. The mobile user is the person who uses the mobile application to perform sign-to-text and text-to-speech translation, and the mobile application can be used immediately upon opening without an account.

The SigLa mobile application contains four (4) modules: Main Interface, Word Bank, Translation History, and Settings. It recognizes motion-based gestures on the device and converts each recognized gesture into text and spoken audio. Translation is performed entirely on the device and produces individual words rather than full sentences. An internet connection is required only to download the latest gesture recognition model and to play a word's demonstration video. When the device is online, the application checks for a newer model and downloads it if a newer version is available, then synchronizes the word bank to match the words supported by that model. Before a downloaded model replaces the active one, the application verifies its integrity against a checksum published by the backend; if the download fails or the file does not match, the previously installed model and its word bank remain in use so that recognition continues to work. After a successful model update, the application prompts the mobile user to restart.

On first launch, the mobile application shows a brief onboarding tutorial covering the main interface, gesture detection, the word bank, and navigation. The tutorial appears only once and can be skipped, and it reappears if the application is reinstalled or its data is cleared. The mobile user can replay it at any time from the settings module.

The main interface module is where the mobile user performs gesture recognition using the device camera. Once the camera is active, gestures are detected and translated automatically, showing the English text with its Filipino translation below it and playing the corresponding audio. The mobile user can hide the Filipino translation with a toggle. After each recognized gesture, the system applies a two-second pause before accepting the next one to avoid repeated detections, so a gesture typically takes about one to three seconds to register. The module also provides a camera-switch control for the front and rear cameras and an emergency button that, when held briefly, plays a full-volume "Help me" audio alert and shows a matching on-screen banner regardless of the current volume setting. A retractable sidebar serves as the navigation menu.

The word bank module lets the mobile user browse the words the application can translate. It provides a search bar and a category filter, and it presents words grouped by category. Selecting a word shows the word, its category, its Filipino translation, a description, and a demonstration video; the video requires an internet connection, while the remaining information is available offline. The mobile user can mark or unmark a word as a favorite, and favorites can be viewed on their own. Favorites are stored only on the current device and are lost on reinstall or when a different device is used. If an administrator deletes a word that a mobile user has favorited, it is removed from that user's favorites on the next synchronization.

The translation history module keeps a record of gestures recognized in past sessions. Each entry shows the translated word, its confidence percentage, and the time it was detected, grouped by date with the most recent first. History is stored on the device up to 200 entries, and older entries are removed automatically as new ones arrive. The mobile user can delete individual entries or clear all history after a confirmation prompt. History is stored independently of the current word database, so entries remain even if the underlying word is later deleted by an administrator, and it is cleared on reinstall or device switch.

The settings module lets the mobile user adjust the volume, choose a male or female voice, and switch between light and dark mode. Audio output is always in English to match the on-screen translation. A reset-to-default option restores the original settings, and the onboarding tutorial can be replayed here. Settings are stored on the device and applied automatically on each launch, and they revert to default on reinstall or device switch.

The SigLa administrator platform is a web-based management interface that requires an internet connection. It supports two account types, the super administrator and the administrator, with different levels of access. The initial super administrator account is created directly in the database by the developers with a starting username, password, and email address that can be updated later. Administrator accounts can only be created by a super administrator, who then provides the login credentials to the assigned person. On first login, an administrator is required to link an email address, verify it with a six-digit code sent to that address, and replace the initial username and password before gaining access to the rest of the platform.

The administrator platform contains different modules depending on the account type. The super administrator has eight (8) modules: Dashboard, Manage Categories, Manage Words, Manage Model, Manage Administrators, Activity Logs, Reports and Analytics, and Account Settings. The administrator has seven (7) of these, without Manage Administrators.

The login page is the entry point to the platform. A user signs in with either a username or an email address together with the correct password. Passwords must be at least eight (8) characters and include at least one letter and one number. After five (5) consecutive failed attempts the account is temporarily locked for five (5) minutes, and each additional cycle of five (5) failed attempts increases the cooldown by another five (5) minutes; a successful login clears the count. From the login page, a user may choose "Forgot Password?" and enter the account's linked email address to receive a six-digit reset code. If the account has no linked email yet, the system advises the user to contact the super administrator. Once the code is verified, the user can set and confirm a new password and is returned to the login page.

The dashboard module is the first page shown after login and adapts to the account type. It presents five summary cards: for the super administrator the first card shows the total number of registered administrators, while for the administrator it shows the account's creation date; the remaining four show the total number of words, gesture samples, and categories, and the current model version. Selecting a card opens the related page. Below the cards, a table lists each trained model version with its accuracy, and a second table shows the signed-in account's own recent activity, most recent first, with the activity type, description, and date. A retractable sidebar provides navigation to the modules available for the account type.

The manage administrators module is available only to the super administrator. It shows four summary cards for the total, active, deactivated, and deleted administrators. A table lists the administrators with their ID, username, masked email address, status, registration date, and action buttons, and it can be filtered by all, deactivated, or deleted accounts. The edit action opens a modal for updating an administrator's username, email address, and password, and the super administrator can also deactivate, reactivate, or permanently delete an account. The module includes a create-administrator action that opens a modal for a username, password, and confirming password; after a confirmation dialog, the account is created and can then be used by the assigned person, who links an email address on first login. All of these changes are recorded in the activity logs.

The manage categories module is available to both account types. It shows three summary cards for the total number of categories, the number currently in use, and the number that are empty. A table lists each category with its name, description, word count, and edit and delete actions. Adding or editing a category opens a modal with fields for the name and description. Typical categories in the system include calendar, color, days, drink, family, food, greeting, letter, number, relationship, and survival.

The manage words module is available to both account types and manages the words together with their gesture samples. It shows summary cards for the total words, active words, words that are ready to activate, and total gesture samples, and it provides a search bar and a category filter. A table lists each word with its label, category, sample count, status, and actions. Adding a word opens a modal for the label, Filipino translation, description, and category, and new words start with no gesture samples. To collect samples, an administrator uploads recorded gesture clips, which the system processes with MediaPipe to extract hand and upper-body landmark sequences that are stored in the database; clips that fail landmark validation are rejected and do not count toward the total. A word must reach at least twenty (20) approved gesture sequences before it becomes eligible for activation, and words are activated when a model trained on their samples is deployed. Editing a word updates its label, translation, description, and category, and deleting a word also removes its gesture samples and demonstration video.

The manage model module is available to both account types and manages the gesture recognition models. It shows three summary cards for the total number of model versions, deployed models, and inactive models, followed by a card describing the currently deployed model, including its version number, accuracy, number of classes, and deployment date. A table lists every model version with its version number, status, accuracy, trainer, training date, and status-dependent actions: a newly trained model offers test, deploy, and delete, while a previously deployed model offers revert and delete. Training a new model requires a version number, which accepts only letters, numbers, dots, dashes, and underscores, and an optional note. Training runs in the background on the machine learning service using the collected gesture data, and only one training session can run at a time; if a run fails, its version is marked as failed and the initiating administrator is informed while the deployed model keeps serving mobile users. A trained model can be tested for accuracy before it is deployed, and deploying a model copies its files to a fixed location, recomputes its integrity checksum, and activates the words it was trained on. If a deployed model performs poorly, an administrator can revert to a previous version, after which the word bank is synchronized to the restored model. All versions are retained so any can be restored, a deployed model cannot be deleted, and at least one deployed model always remains active.

The activity logs module is available to both account types and provides a read-only audit trail. A table lists who performed each action, the action type, the affected item, a short description, and the date and time, ordered with the most recent first, and it can be filtered by action type, affected item, and date range. Recorded actions include adding, editing, deleting, or activating words, uploading gesture samples, training, testing, deploying, or reverting models, managing administrator accounts, and signing in. Records are retained indefinitely to preserve the audit trail.

The reports and analytics module is available to both account types and summarizes system growth. It shows four summary cards for the total words, gesture samples, categories, and the current model accuracy, and a line chart of word and sample growth over time that can be viewed by week, month, or year. A table lists the model version history with each version number, accuracy, and creation date. A generate-report action lets an administrator choose which data to include, such as word statistics, gesture sample counts, and model accuracy, along with a time period, and exports the selection as a PDF document.

The account settings module is available to both account types and shows the account's own username, masked email address, and account type. An edit-profile action allows the username to be changed. If no email address is linked yet, an add-email action is offered; otherwise a change-email action is offered, and both require verifying the address with a six-digit code before it is saved. A change-password action requires a six-digit verification code sent to the linked email before a new password can be set, subject to the same rules as login.

The system architecture consists of the SigLa mobile application, the SigLa administrator platform, the SigLa backend server, the SigLa machine learning component, and the PostgreSQL database. The mobile application contacts the backend to fetch the current word bank and model updates. The backend server exposes a REST API that connects the mobile application, the administrator platform, the machine learning component, and the database, and it also delegates training, testing, and deployment to the machine learning component. The mobile application performs recognition locally using a downloaded TFLite model, while the backend manages words, categories, models, and their distribution.

The system is developed using Kotlin for the Android mobile application, React.js for the web-based administrator platform, Node.js with Express.js for the backend server, and Python for the machine learning component, with PostgreSQL as the database management system and Supabase for database hosting and file storage. Development tools include Android Studio, Visual Studio Code, Postman, and GitHub.

The proponents acknowledge that gesture recognition performance is affected by device capability and environmental conditions, and the system is designed to perform reasonably within these factors, with more capable devices generally performing better. The system aims for accurate translations, but occasional errors may occur, and results can be affected by poor lighting, a dirty or damaged lens, obstruction, or excessive distance between the camera and the hands. The system supports FSL gestures only, displays translated text in English with a Filipino translation, and produces individual words rather than full sentences or continuous conversation. The English text exists to make a recognized gesture more broadly understandable, since many FSL gestures correspond to concepts commonly expressed in English, while the recognition, dataset, and translation remain based entirely on FSL. Each recognized gesture is mapped to a predefined word from the trained dataset, and variations in hand structure, such as missing or irregular fingers, may affect accuracy.

For optimal recognition, the distance between the camera and the hands should not exceed 0.5 meters. The system supports both left-handed and right-handed users and gestures that use one or both hands, recognizing up to two hands at a time. It requires a stable internet connection of at least 10 Mbps for server-dependent features such as loading the latest word bank and downloading model updates. Recommended mobile specifications include a 13-megapixel camera, at least 6 GB of RAM to run the camera, landmark detection, and recognition together, and Android 7.0 (Nougat) or higher. The SigLa mobile application is developed exclusively for Android and does not support iOS or any other mobile operating system.
