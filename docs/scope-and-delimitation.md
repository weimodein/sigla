3.4 Scope and Delimitation

The proponents developed SigLa, a Mobile Sign Language Translator Application for Persons with Speech and/or Hearing Disability. SigLa supports one-way communication, translating Filipino Sign Language (FSL) gestures captured through a device camera into on-screen text and spoken audio so that sign language users can be understood by non-signers. It is intended as an accessible tool for everyday interactions that reduces heavy reliance on human interpreters. The system operates both online and offline, and it keeps all supported words, gesture sample data, administrator accounts, trained models, and activity records in a centralized PostgreSQL database that supports translation updates and system monitoring.

The system recognizes three (3) types of users, namely the Super Administrator, the Administrator, and the Mobile User. The super administrator has full access to the administrator platform, including managing all administrator accounts, viewing the dashboard, managing categories, managing words in the word bank, managing the gesture recognition model, viewing the activity logs, viewing reports and analytics, and managing its own account credentials. The administrator has the same access apart from managing other administrator accounts, which remains reserved for the super administrator. The mobile user is the person who uses the mobile application to perform sign-to-text and text-to-speech translation, and the mobile application can be used immediately upon opening without an account.

The SigLa mobile application contains four (4) modules, namely Main Interface, Word Bank, Translation History, and Settings. It recognizes motion-based gestures on the device and converts each recognized gesture into text and spoken audio. Translation is performed entirely on the device and produces individual words rather than full sentences. An internet connection is required only to download the latest gesture recognition models and to play a word's demonstration video. When the device is online, the application checks whether the deployed version differs from the one it holds and downloads the new version if it does, and this check is limited to once every five (5) minutes so that leaving and reopening the recognition screen repeats it only when the interval has passed. The word bank always follows the deployed version, since the server derives the list of available words from the version currently deployed, so the words shown on the device are exactly the words that version was trained to recognize. This applies in both directions, so that if an administrator reverts to an earlier version, the word bank returns to that version's words and advertises only what the version recognizes. Before a downloaded model replaces the active one, the application verifies its integrity against a checksum published by the backend. Should the download fail or the file differ from the checksum, the previously installed model and its word bank remain in use so that recognition continues to work. After a newer version is downloaded and verified, the application loads it immediately and refreshes the word bank in the same step, and the main interface displays its loading progress before gesture recognition becomes available.

A trained version consists of two (2) separate recognition models, one for the main vocabulary and one for the fingerspelling alphabet. The two are kept apart because several FSL signs are formed from a letter, as each day of the week is its first letter traced in a circular motion, so a letter and the day sign built from it differ only in movement. Measurement on the collected data showed the letter M and the sign for MONDAY to be closer together than any two day signs are to each other, which means a single list of classes carrying both would confuse them. The two models are therefore trained in one run, deployed together, and reverted together, so the device always holds the main vocabulary and the alphabet from the same version. On the device, the main interface offers a vocabulary switch that appears once an alphabet model is installed, allowing the mobile user to choose between signing words and spelling letters. Switching clears any partially captured gesture so that a movement begun in one mode is interpreted only in that mode.

On first launch, the mobile application shows a brief onboarding tutorial covering the main interface, gesture detection, the word bank, and navigation. The tutorial appears only once and can be skipped, and it reappears if the application is reinstalled or its data is cleared. The mobile user can replay it at any time from the settings module.

The main interface module is where the mobile user performs gesture recognition using the device camera. Once the camera is active, gestures are detected and translated automatically, showing the English text with its Filipino translation below it and playing the corresponding audio. The mobile user can hide the Filipino translation with a toggle placed beside the vocabulary switch. After each recognized gesture, the system applies a two-second pause before accepting the next one to avoid repeated detections, so a gesture typically takes about one to three seconds to register. The module also provides a camera-switch control for the front and rear cameras and an emergency button that, when held briefly, plays a full-volume "Help me" audio alert and shows a matching on-screen banner at any current volume setting. Because the recognition model is trained on gestures sampled at a fixed rate, the application requests a camera frame rate of at least twenty-four (24) frames per second and reports to the mobile user whenever the device falls below it, since a slower camera stretches every gesture and reduces recognition accuracy. A retractable sidebar serves as the navigation menu.

The word bank module lets the mobile user browse the words the application can translate. It provides a search bar and a category filter, and it presents words grouped by category, including the fingerspelling alphabet as its own category. Selecting a word shows the word, its category, its Filipino translation, a description, and a demonstration video. The video requires an internet connection, while the remaining information is available offline. The mobile user can mark or unmark a word as a favorite, and favorites can be viewed on their own. Favorites are stored only on the current device and last until the application is reinstalled or a different device is used. If an administrator deletes a word that a mobile user has favorited, it is removed from that user's favorites on the next synchronization.

The translation history module keeps a record of gestures recognized in past sessions. Each entry shows the translated word, its confidence percentage, and the time it was detected, grouped by date with the most recent first. History is stored on the device up to two hundred (200) entries, and older entries are removed automatically as new ones arrive. The mobile user can delete individual entries or clear all history after a confirmation prompt. History is stored independently of the current word database, so entries remain even after an administrator deletes the underlying word, and the history is cleared on reinstall or device switch.

The settings module lets the mobile user adjust the volume, choose a male or female voice, and switch between light and dark mode. Audio output is always in English to match the on-screen translation. A reset-to-default option restores the original settings, and the onboarding tutorial can be replayed here. Settings are stored on the device and applied automatically on each launch, and they revert to default on reinstall or device switch.

The SigLa administrator platform is a web-based management interface that requires an internet connection. It supports two account types, the super administrator and the administrator, with different levels of access. The initial super administrator account is created automatically when the backend server starts, using credentials held in the server's configuration, and these can be updated later. Administrator accounts can only be created by a super administrator, who then provides the login credentials to the assigned person. On first login, an administrator is required to link an email address, verify it with a six-digit code sent to that address, and replace the initial username and password before gaining access to the rest of the platform.

The administrator platform contains different modules depending on the account type. The super administrator has eight (8) modules, namely Dashboard, Manage Categories, Manage Words, Manage Model, Manage Administrators, Activity Logs, Reports and Analytics, and Account Settings. The administrator has seven (7) of these, excluding Manage Administrators.

The login page is the entry point to the platform. A user signs in with either a username or an email address together with the correct password. Passwords must be at least eight (8) characters and include at least one letter and one number. After five (5) consecutive failed attempts the account is temporarily locked for five (5) minutes, and each additional cycle of five (5) failed attempts increases the cooldown by another five (5) minutes, while a successful login clears the count. From the login page, a user may choose "Forgot Password?" and enter the account's linked email address to receive a six-digit reset code. For an account that still lacks a linked email, the system advises the user to contact the super administrator, who can set a temporary password for them from the manage administrators module. Once the code is verified, the user can set and confirm a new password and is returned to the login page.

The dashboard module is the first page shown after login and adapts to the account type. It presents five summary cards, where the first card shows the total number of registered administrators for the super administrator and the account's creation date for the administrator, while the remaining four show the total number of words, gesture samples, and categories, and the current model version. Selecting a card opens the related page. Below the cards, a table lists each trained version with the accuracy of its main vocabulary model, and a second table shows the signed-in account's own recent activity, most recent first, with the activity type, description, and date. A retractable sidebar provides navigation to the modules available for the account type.

The manage administrators module is available only to the super administrator. It shows four summary cards for the total, active, deactivated, and deleted administrators. A table lists the administrators with their ID, username, masked email address, status, registration date, and action buttons, and it can be filtered by all, deactivated, or deleted accounts. The edit action opens a modal showing the administrator's details, where the super administrator can update the username and the email address directly. When the email address is changed, a notification is sent to both the old and the new address so the affected administrator learns of any change made on their behalf. The password is shown only as a masked placeholder and remains untypeable in this form. Instead, a reset-password action lets the super administrator set a temporary password to hand over to the administrator directly, which restores access to an account whose owner has lost the ability to receive email. Because a super administrator who knew another account's lasting password could sign in as that person and leave the activity logs unable to prove who performed an action, the temporary password expires on use, so the administrator must choose their own new password before reaching any module and the super administrator's knowledge of it stops being useful the moment it is used. Only an account that still lacks a linked email address is additionally asked to link and verify one at that point, while an administrator who already has a verified email keeps it and is asked only for a new password. The super administrator can also deactivate, reactivate, or permanently delete an account. Every change to an administrator's account sends a notification to their linked email address, whether the super administrator made the change or the administrator made it themselves, covering the username, the email address, the password, and the account status of being deactivated, reactivated, or removed. A change of email address notifies both the old and the new address, so an administrator still learns of a change made from a session that belongs to someone else. The notification omits any password or verification code, and an account that still lacks a linked email address can be notified only once it links one. The module includes a create-administrator action that opens a modal for a username, password, and confirming password, and after a confirmation dialog the account is created and can then be used by the assigned person, who links an email address on first login. All of these changes are recorded in the activity logs.

The manage categories module is available to both account types. It shows three summary cards for the total number of categories, the number currently in use, and the number that are empty. A table lists each category with its name, description, word count, and edit and delete actions. Adding or editing a category opens a modal with fields for the name and description. Typical categories in the system include alphabet, calendar, days, family, greeting, number, and survival.

The manage words module is available to both account types and manages the words together with their gesture samples. It shows summary cards for the total words, active words, words that are ready to activate, and total gesture samples, and it provides a search bar and a category filter. A table lists each word with its label, category, sample count, status, and actions. Adding a word opens a modal for the label, Filipino translation, description, and category, and new words start with an empty set of gesture samples. Each word also records which of the two models it belongs to, the main vocabulary or the fingerspelling alphabet, and this is set when the word is created rather than inferred from its spelling, because the Filipino alphabet includes a letter written with two characters that a spelling rule would classify incorrectly. To collect samples, an administrator uploads recorded gesture clips, which the system processes with MediaPipe to extract hand and upper-body landmark sequences that are stored in the database, while clips that fail landmark validation are rejected and are excluded from the total. Validation also discards individual frames in which the detected hand is implausibly large, which occurs when the landmark detector briefly collapses and would otherwise store a distorted frame that later checks would treat as valid. Uploads are processed in the background as a tracked job so that a batch survives the administrator navigating away, and one upload may run for a word at a time. A word must reach at least twenty (20) approved gesture sequences before it becomes eligible for activation, up to a maximum of twenty-five (25) samples per word, and words are activated when a version trained on their samples is deployed. Editing a word updates its label, translation, description, and category, and deleting a word also removes its gesture samples and demonstration video.

The manage model module is available to both account types and manages the gesture recognition models. It shows three summary cards for the total number of versions, deployed versions, and versions awaiting deployment, counted per version rather than per model so that a version's two models are reported once. A card below them describes the currently deployed version, including its version number, accuracy, number of classes, and deployment date. A table lists every version with its version number, status, accuracy, trainer, training date, and status-dependent actions, where a newly trained version offers deploy and delete, while a previously deployed version offers revert and delete. A version that also produced an alphabet model is marked as such, and expanding its row shows that model's own accuracy and class count separately, since an accuracy measured over twenty-six (26) letters differs in meaning from one measured over the whole vocabulary. Training a new version requires a version number, which accepts only letters, numbers, dots, dashes, and underscores, and an optional note. One training run produces both models, where the main vocabulary model is trained first and the alphabet second, so that a failure in the shorter alphabet run preserves the longer one. Training runs in the background on the machine learning service using the collected gesture data, and one training session can run at a time. Should a run fail, its version is marked as failed and the initiating administrator is informed while the deployed version keeps serving mobile users. Deploying a version copies its files to storage, recomputes its integrity checksum, and activates the words it was trained on, and it deploys both of the version's models together, so that deployment requires a version whose alphabet also trained successfully. Each trained version records the words it was trained on, and the mobile word bank is derived from whichever version is deployed. If a deployed version performs poorly, an administrator can revert to a previous one, and both the word bank and the alphabet return to that version's contents automatically. All versions are retained so any can be restored, deletion is limited to versions other than the deployed one, and at least one deployed version always remains active.

The activity logs module is available to both account types and provides a read-only audit trail. A table lists who performed each action, the action type, the affected item, a short description, and the date and time, ordered with the most recent first, and it can be filtered by action type, affected item, and date range. Recorded actions include adding, editing, deleting, or activating words, uploading gesture samples, training, deploying, or reverting versions, managing administrator accounts, and signing in. Entries for training, deploying, reverting, and deleting a version state whether the version's alphabet model was included, so the log reflects that both models moved together. Records are retained indefinitely to preserve the audit trail.

The reports and analytics module is available to both account types and summarizes system growth. It shows four summary cards for the total words, gesture samples, categories, and the current model accuracy, the last of which reports the main vocabulary model so that the figure always describes the system's overall accuracy. A line chart shows word and sample growth over time and can be viewed by week, month, or year, and a second chart plots accuracy by version with the alphabet shown as a separate series. A table lists the version history with each version number, the accuracy of both of its models, and its creation date. A generate-report action lets an administrator choose which data to include, such as word statistics, gesture sample counts, and model accuracy, along with a time period, and exports the selection as a PDF document.

The account settings module is available to both account types and shows the account's own username, masked email address, and account type. An edit-profile action allows the username to be changed. An add-email action is offered while the account still lacks a linked address, and a change-email action is offered once one exists, and both require verifying the address with a six-digit code before it is saved. A change-password action requires a six-digit verification code sent to the linked email before a new password can be set, subject to the same rules as login.

The system architecture consists of the SigLa mobile application, the SigLa administrator platform, the SigLa backend server, the SigLa machine learning component, and the PostgreSQL database. The mobile application contacts the backend to fetch the current word bank and model updates. The backend server exposes a REST API that connects the mobile application, the administrator platform, the machine learning component, and the database, and it also delegates training and deployment to the machine learning component. The machine learning component validates a version's files and reports their locations, while the backend alone decides which version is active, so that a single component governs the deployed version at any time. The mobile application performs recognition locally using downloaded TFLite models, while the backend manages words, categories, models, and their distribution. Because the same landmark extraction is used for uploaded clips and for live recognition, a gesture recorded for training and the same gesture performed in front of the camera are converted into the same form, and automated tests compare the two implementations so that a change made to one is mirrored in the other.

The system is developed using Kotlin for the Android mobile application, React.js for the web-based administrator platform, Node.js with Express.js for the backend server, and Python for the machine learning component, with PostgreSQL as the database management system and Supabase for database hosting and file storage. Development tools include Android Studio, Visual Studio Code, Postman, and GitHub.

The proponents acknowledge that gesture recognition performance is affected by device capability and environmental conditions, and the system is designed to perform reasonably within these factors, with more capable devices generally performing better. The system aims for accurate translations, while occasional errors may occur, and results can be affected by poor lighting, a dirty or damaged lens, obstruction, or excessive distance between the camera and the hands. Low light is a particular limitation because the camera lengthens its exposure and reduces its frame rate to compensate, which slows the captured gesture relative to the recordings the model was trained on. The system supports FSL gestures alone, displays translated text in English with a Filipino translation, and produces individual words rather than full sentences or continuous conversation. The English text exists to make a recognized gesture more broadly understandable, since many FSL gestures correspond to concepts commonly expressed in English, while the recognition, dataset, and translation remain based entirely on FSL. Each recognized gesture is mapped to a predefined word from the trained dataset, and variations in hand structure, such as missing or irregular fingers, may affect accuracy. Signs that differ only in a small detail remain the hardest to separate, and the fingerspelling alphabet is kept in its own model for this reason.

For optimal recognition, the distance between the camera and the hands should remain within 0.5 meters. The system supports both left-handed and right-handed users and gestures that use one or both hands, recognizing up to two hands at a time. Support for both hands and for the front camera is achieved by training on mirrored copies of the collected recordings, so the orientation a mobile user signs in may differ from the orientation in which the dataset was recorded. It requires a stable internet connection of at least 10 Mbps for server-dependent features such as loading the latest word bank and downloading model updates. Recommended mobile specifications include a 13-megapixel camera, at least 6 GB of RAM to run the camera, landmark detection, and recognition together, and Android 7.0 (Nougat) or higher. The SigLa mobile application is developed exclusively for Android and supports Android alone among mobile operating systems.
