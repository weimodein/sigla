3.4 Scope and Delimitation

The proponents developed SigLa, a Mobile Sign Language Translator Application for Persons with Speech and/or Hearing Disability. SigLa supports one-way communication by turning supported Filipino Sign Language (FSL) gestures into on-screen text and spoken audio. The system is made for common daily interactions between FSL users and people who use spoken communication. It includes an Android mobile application, a web-based administrator platform, a backend server, a machine learning service, a PostgreSQL database, and file storage for models and media.

The system has three (3) types of users: the Super Administrator, the Administrator, and the Mobile User. The super administrator can use every part of the web platform, including administrator account management. The administrator can manage categories, words, gesture samples, demonstration videos, and recognition models, and can view activity logs, reports, and account settings. The mobile user can open the Android application as a guest and use its translation and word-learning features.

The SigLa mobile application has four (4) main modules: Main Interface, Word Bank, Translation History, and Settings. Gesture recognition runs on the mobile device through downloaded TensorFlow Lite models and label files. The first model download needs internet access. After the model pair and word data are saved, the main translation feature can work offline. Internet access is used for model updates, word and category updates, video streaming, and video downloads.

Each trained version has two (2) recognition models. The words model handles the main vocabulary, while the letters model handles the FSL fingerspelling alphabet. This setup helps separate letters from word signs that use a similar hand shape with added movement. Both models are trained under one version number, deployed together, restored together, and removed together. The Main Interface shows a Words and Letters switch after a complete model pair has been loaded. Changing the vocabulary clears the gesture currently being read and starts a fresh capture for the chosen model.

When the Main Interface opens, the application checks the model version stored on the device against the active version from the server. A successful check is reused for up to five (5) minutes. A version change starts the download of both models and their label files. The application places the files in a temporary folder, checks the model checksum when the server provides one, checks the label files, and activates the full set in one step. If the update stops, the saved model pair stays active. After a version change, the application refreshes the word bank so its entries match the words and letters recorded for the active version.

On first use, the mobile application shows an onboarding guide for the Main Interface, gesture detection, Word Bank, and navigation. The mobile user may skip the guide and replay it from Settings. The application saves the guide status on the device. Clearing the application data starts the guide again, while Android backup settings may restore saved local data after reinstallation or device transfer.

The Main Interface module uses the device camera to read hand and upper-body landmarks. Once the model is ready, the application watches the gesture movement and shows an accepted result in English. A Filipino translation appears below the English label when one is available and the Filipino display is enabled. The device text-to-speech engine reads the English result aloud. After an accepted gesture, the system waits two (2) seconds before accepting the next result. The module also allows the user to change between the front and rear cameras.

The Main Interface includes an emergency button. Holding the button for two (2) seconds plays the phrase “Help me” through the device text-to-speech engine and shows an emergency alert message. The sound follows the volume saved in the application and the speech settings available on the device. The application requests a camera rate of at least twenty-four (24) frames per second because the recognition process uses the timing of each movement. A warning appears when the camera rate becomes too low, helping the user improve the lighting or camera view. A side menu gives access to the other mobile modules.

The Word Bank module shows the vocabulary linked to the active model version. It includes category cards, All Words, Favorites, a search field, and a category filter. Selecting an entry opens its English label, Filipino translation, description, category, and available demonstration media. A demonstration video can be streamed through the internet or downloaded for offline viewing. The user can also download all available videos, cancel a group download, and clear saved video copies after the full set has been downloaded.

The mobile user can add or remove a word from Favorites. Favorite word IDs are saved on the device. The Favorites view shows saved items that still belong to the current word list. Word details, categories, favorites, and downloaded media use local storage for offline access. Their recovery after reinstallation or transfer depends on Android backup and the saved application data.

The Translation History module keeps up to two hundred (200) recognized entries on the device. Each displayed entry shows the recognized word and the time of detection. Entries are grouped by date, with the latest records shown first. When the limit is reached, a new entry replaces the oldest entry. The mobile user can remove one entry by swiping or using its delete button, and can clear the full history after a confirmation step. History is kept apart from the server word bank, so earlier records can stay when the active vocabulary changes.

The Settings module allows the mobile user to set the speech volume, choose a male or female English voice, and use light or dark mode. The chosen voice depends on the English voices installed through the device text-to-speech engine. A reset option returns the settings to their starting values. The user can also replay the onboarding guide. These choices are saved on the device and may be included in Android backup.

The SigLa administrator platform is a web application that uses an internet connection. It supports super administrator and administrator accounts. The backend creates the first super administrator from the server setup when the account is still absent. The super administrator creates other administrator accounts and gives the first username and password to each assigned person. During first login, the administrator links and verifies an email address through a six-digit code, then chooses the username and password used for later access.

The super administrator has eight (8) modules: Dashboard, Manage Administrators, Manage Words, Manage Categories, Manage Model, Activity Logs, Reports, and Administrator Account. The administrator has seven (7) modules, with Manage Administrators reserved for the super administrator. Both account types can manage their own profile and security settings.

The Login page accepts a username or email address together with a password. A username contains three (3) to fifty (50) characters and uses no whitespace. A password contains eight (8) to sixty-four (64) characters, with at least one letter and one number. Spaces may appear between password characters, while the beginning and end stay free of whitespace. After every five (5) consecutive incorrect password entries, the account enters a timed lock. The first lock lasts five (5) minutes, and each later lock adds another five (5) minutes. A successful login clears the attempt and lock count. Logging out sends the current access token to the backend revocation list and ends the session.

The Forgot Password page lets an account holder request a six-digit code through the linked email address. The code is checked before a new password is accepted. Verification codes expire after five (5) minutes, allow up to five (5) incorrect entries, and use a one-minute wait before another code request. An account with a linked email can also receive a notice after a password change. For an administrator who needs direct help, the super administrator can set a temporary password through Manage Administrators.

The Dashboard is the first main page after login and completed account setup. It shows the active model version and summary cards for words, gesture samples, and categories. For the super administrator, another card shows the total number of active and deactivated administrator accounts. For an administrator, that card shows the account creation date. The page also shows accuracy bars for up to eight (8) recent words models and a list of the signed-in account’s recent actions. Cards with linked modules open their matching pages.

The Manage Administrators module is available to the super administrator. It shows totals for all current administrators, active accounts, deactivated accounts, and deleted accounts. A searchable and filterable table lists each account’s ID, username, masked email address, status, registration date, and actions. The super administrator can create an account, edit its username or email address, reset its password, deactivate it, reactivate it, or mark it as deleted. Account deletion uses a deleted status so activity records can keep their account link.

Creating an administrator requires a username, password, matching password entry, and confirmation. A password reset creates a temporary password and sends the administrator through account setup on the next login. An administrator with a linked email keeps that address during this setup, while a new account completes email linking first. The system records account changes in the activity logs and sends account notices to linked email addresses. When an email address changes, the service sends notices to the old and new addresses when delivery succeeds.

The Manage Categories module is available to both administrator account types. It shows the total number of categories, categories used by words, and empty categories. Its table lists the category name, description, word count, and edit and delete actions. Adding or editing a category uses fields for its name and description. A category assigned to one or more words stays protected from deletion until its words are moved to another category or removed.

The Manage Words module is available to both administrator account types. It shows totals for vocabulary entries, active words, words ready for training, and gesture samples. It also provides search, category filtering, sorting, page controls, and a table of word records. A word record contains an English label, Filipino translation, description, category, and a vocabulary type of Words or Letters. The vocabulary type places the record in the matching recognition model. Administrators can add, edit, or delete a word, clear its training samples, and set one demonstration video for the mobile Word Bank.

Gesture samples are uploaded as video clips with a signer ID for the person shown in the batch. The backend starts a tracked upload job, while the machine learning service uses MediaPipe to turn each clip into a sequence of hand and upper-body landmarks. The service checks landmark coverage, movement, sample shape, and repeated data before saving an approved sequence. The current rules use at least twenty (20) approved clips for each vocabulary entry, at least four (4) signers, and at least four (4) approved clips from each counted signer. The normal total limit is twenty-five (25) clips for each entry. These values can be changed through server settings. A word becomes active for mobile users when it belongs to a deployed model version.

The Manage Model module is available to both administrator account types. It shows the number of model versions, the active version, and versions ready for deployment. It also shows the active words model with its version, accuracy, class count, and deployment date. A table groups the words model and letters model under one version. Each row shows both accuracy values, status, trainer, and training date, with more details available inside the row.

Training starts after an administrator enters a unique version name made of letters, numbers, dots, dashes, or underscores. An optional note may describe the changes. The backend creates the words and letters records together, starts the work in the background, and reports progress to the web page. The words model trains first, followed by the letters model. A version becomes ready for deployment after both models finish and their files are available. The accuracy values describe the test data used by the training process and serve as model guides rather than a promise for every live camera setting.

Deploying a version checks both model files, their label files, and their recorded vocabulary. The backend copies the files to storage, creates their checksums, marks the chosen pair as active, and updates the mobile word list to the entries used by that version. An administrator can restore an earlier complete version, which brings back its words model, letters model, and matching word list. A trained or older inactive version can be deleted as a pair. The active version stays protected while it serves mobile users.

The Activity Logs module is available to both administrator account types as a view-only record of system actions. It shows the administrator, action type, affected item, description, date, and time. Users can search the records and filter them by action, item type, and date range. Logged actions include sign-in, account setup, account management, category changes, word changes, sample uploads, password recovery, and model training, deployment, restore, and deletion. The database keeps these records for review and system maintenance.

The Reports module is available to both administrator account types. It shows summary cards for vocabulary entries, gesture samples, categories, and the active model pair. Charts show vocabulary submissions over a selected period, words and letters accuracy by model version, and current sample coverage for the ten (10) entries with the highest sample counts. The super administrator also sees lists of deactivated and deleted administrator accounts. The Generate Report section can include vocabulary data, gesture sample data, and model accuracy data in a PDF file.

The Administrator Account module shows the signed-in account’s username, masked email address, account type, creation date, status, role, and account ID. The account holder can change the username. Adding or changing an email address requires a six-digit verification code sent to the new address. Changing the password requires a code sent to the linked email address, followed by a new password and matching confirmation. A successful password change returns the account holder to the Login page.

The system uses a client-server structure. The Android application requests the active word bank, categories, and model files from the backend. The web platform uses the backend to manage users, words, samples, categories, models, logs, and reports. The backend stores system records in PostgreSQL and sends training and file tasks to the machine learning service. Supabase Storage holds model and media files. Recognition stays on the Android device after the required model files are installed.

The Android application is written in Kotlin. The administrator platform uses React.js. The backend uses Node.js with Express.js, while the machine learning service uses Python, FastAPI, TensorFlow, and MediaPipe. PostgreSQL manages the main records, and Supabase provides the configured database and file storage services. The project uses Android Gradle, Vite, Node.js, and Python tools for development and testing.

The scope of gesture recognition covers the FSL words and letters included in the trained dataset. The application gives one vocabulary result at a time, including labels that may contain several written words. Sentence building, full conversation translation, and two-way spoken-language translation remain outside the current project scope. Recognition uses hand and upper-body landmarks. Facial expressions, lip movement, and full body movement stay outside the model input used by the current code.

Recognition quality depends on the training samples, signer range, hand shape, signing style, device speed, camera quality, lighting, distance, and framing. A clear view of the hands and upper body gives the landmark tracker better input. The detector can follow up to two hands and supports front and rear cameras. Mirrored training data helps cover changes in hand direction, while live results still depend on how well the training set represents each user and gesture.

The mobile application targets Android devices and declares Android 7.0, API level 24, as its lowest supported version. A working camera is required. Device storage is used for models, labels, word data, favorites, history, settings, images, and downloaded videos. Server-based features require an internet connection, and their speed depends on the connection, file size, server access, and device performance. Support for other mobile operating systems remains outside the current project scope.
